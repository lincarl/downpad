# md-easy design

This document describes the main design of md-easy. It intentionally omits internal API listings, historical migration notes, and development plans.

## Technology

md-easy is an Electron desktop application:

- The frontend uses React and TypeScript.
- Milkdown Crepe provides the WYSIWYG Markdown editor.
- CodeMirror provides the Markdown source editor.
- The TypeScript main process handles native file access, settings, recovery data, printing, and desktop integration.
- Local application data is stored in human-readable or standard formats such as Markdown, TOML, and JSON.
- pnpm applies the fixes in `patches/` to dependencies on install. Each patch explains itself in a comment. The ProseMirror patch keeps a caret key such as End, pressed right after a click into the document view, from being undone on a busy machine. The Milkdown components patch keeps text typed right after Tab, Shift+Tab, Enter, undo or redo in a list where it was typed. Each of these redraws a list item, which puts back the caret it saw then once the next frame comes. On a busy machine that frame can come after keys typed meanwhile, and the caret jumped back into them, so a key, click or edit before the frame now cancels it.

Electron packages Chromium and Node.js with the app. This gives development and installed builds the same browser runtime at the cost of a larger installer.

## Editing model

Each open document has one canonical Markdown string. The document and source editors are two views of that same content:

- Document view renders and edits formatted Markdown.
- Markdown view exposes the source directly. It parses GitHub Flavored Markdown with a leading YAML frontmatter block, and colors it with VS Code's default Markdown and YAML token colors (Light+ and Dark+). It reads display math in `$$` fences outside lists and quotes as the document view does, with blank lines in the math and math that is not closed running to the end of the text, and leaves the math in the body color.
- Split view shows both and synchronizes changes between them.

If the document view cannot be built for a tab, because Milkdown's create fails (for example when the parser overflows its stack on deeply nested quotes), the tab records the error and shows its Markdown view alone, whatever the window's layout. The layout control shows Markdown while that tab is active, and the window's layout and the `defaultView` setting stay as they are. The notice bar under the tabs explains the fallback and offers Try again. Any other banner, such as a file changed on disk, takes the bar first. Try again, choosing Document or Split, or reloading the file builds the document view again from the tab's current text. A failed create still ends, because md-easy skips Milkdown's destroy for an editor that is still creating. That destroy would otherwise try again every 50 ms forever. The print workspace prints the Markdown version of a document it cannot render.

Building the document view can take a moment, for example while local images are looked up, and the Markdown view on screen stays editable meanwhile. If the text or a document setting changes during the build, md-easy builds the view again from the current text and settings before it shows it. So the document view never shows older text, and its edits always reach the tab. If the text changes during each of five builds in a row, md-easy stops and shows the tab's Markdown view with the notice, as for a failed create.

Reloading a file from disk, or opening a file in place of an empty Untitled tab, replaces the tab's text. While the document view is built for the new text, the Markdown view on screen still holds the old text, so md-easy ignores typing there until that view is built again too. That typing would otherwise write the old text back over the new. Each view is built again from the new text when it is next shown. Its undo history starts there, and the document view looks its images up again, so an image that has appeared on disk shows. md-easy drops a split mirror of an edit made before the new text arrived. That mirror would copy the new text into a view built before it and count that view as up to date, with its undo history and image answers from before.

md-easy changes the views one step at a time, such as a tab switch, a layout switch or a reload. A tab switch, an open, a reload or a layout choice that comes while another step still builds a view waits for that step, and md-easy then shows the active tab again, in the layout the layout control shows. So the window never keeps showing another tab's Markdown view, where typing would be ignored, and a view built from the text before a reload is built again from the new text. A layout or a tab chosen while a layout switch, Try again or a tab switch still runs is ignored, and the layout control and the tabs stay as they were. A layout switch or a tab switch that waits for another step counts as running until md-easy shows the active tab. So once a layout is chosen during a reload, another layout or a tab chosen before the document shows is ignored.

Opening a document never changes its text. The document view reports the exact source it was given until the user edits the body there. An edit there writes only the top-level blocks it changed in Milkdown's Markdown style. Every other block keeps its source text. Two blocks that were neighbours in the source keep the blank lines between them. A new join, next to a changed or removed block, keeps the source's line break when the text still reads as the same blocks, and otherwise gets a blank line. Link reference definitions, which the document view does not show, stay while a block that keeps its source text uses them. A definition that nothing in the source used stays as long as any block keeps its source text.

The document view pairs its blocks with the source's blocks. Blocks the user did not touch are the same ProseMirror nodes as when the source was parsed, and the rest pair by how Milkdown writes them. The positions of the source's blocks come from the parse that opened it. Every new join is checked before the text is used. Rules that follow from how the parser ends each kind of block settle most joins without reading anything back, for example a blank line after a paragraph or a closed fence. The other joins are read back with Crepe's parser, in a window that starts where the text above cannot change how it reads and ends with the first lines of the block below. The window must read as exactly its blocks. A block that keeps its source text must read as the same kind of node over the same text and open the same blocks on its first line, such as a quote with a list in it. A changed block must read as the document's block in Milkdown's form, or as that form reads on its own. Each block's text ends on its last line, and the line break after it stays with the blank lines below it. In a file with no line break at its end, a kept block that becomes the last one keeps the line break that followed it, because a tag alone on the last line of a list, quote or footnote reads as part of it only with a line break after it. Where a window reads otherwise, the join at fault gets a blank line and the window is read again. The document view writes the whole body in Milkdown's style when a window still reads otherwise (a new list right below a list, for example), when a changed block held a definition, when a new footnote could turn text in a kept block into a reference, when raw HTML in a changed block holds a line that could be a definition and a kept block has bracketed text it could turn into a link or footnote, when a definition the file keeps could turn bracketed text in a changed block into a link, when indented code could end in another place than in the source, as it can right below a list or quote, when text follows a block that read as it did only at the very end of the file, when the text below a list or footnote that ends in a fence, math block or HTML block the file left open, such as a comment with no `-->` or a `<pre>` with no `</pre>`, would change what that block holds, when the source's blocks do not map one for one onto the document's, or when reading the windows back would take longer than writing the whole body. The same document always gets the same text, whatever was written before it. A split mirror sync makes the synced text the new source and records that with the body in the undo history, so undoing a sync writes the body from before it with that body's own source.

The document view shows the YAML frontmatter in an editable table above the editor. The table writes back only the lines it changes. Each change to the block is a step in the editor's undo history, so undo and redo move through table and body edits in one order. A split mirror sync records the block and the blank lines after it with the body, so its undo restores all three.

Crepe's table view turns a click on a cell's text, or in the space right of it, into a selection of the cell's whole paragraph a frame later, unless the caret is already in that cell. The next keystroke then replaced the cell's text. md-easy replaces that view with a subclass that leaves a press inside the cells to ProseMirror, as in any paragraph, and to prosemirror-tables, which selects cells on a drag across them or out of the table. Crepe's row and column handles sit outside the cells and keep Crepe's handling.

Crepe's view also had ProseMirror draw a table again, with new cells, whenever only the selection or highlights in it changed. In the split, a click in the document pane right after a Markdown edit first brings that pane up to date, which ends a cell selection there. The click then landed on a cell that was gone, placed no caret, and left the focus in neither pane. The subclass updates a table whose content is unchanged in place, unless a whole row or column is selected in it. Crepe's new view opens the menu of a selected row or column, such as after a click on its handle, on the button that adds it, or a drag of it by its handle, so then the table is still drawn again. After every other update, whether the content changed or not, the subclass closes a row or column menu once the selection it acts on is gone. The redraw did that only when the content was unchanged, so a menu stayed open after a Markdown edit of a cell in the split. Crepe's menu buttons act on pointerdown, and the click that follows reaches the handle, which selects the row or column at its place. After a row's Delete that is the row that moved up, and Crepe's new view opens its menu, so Delete again removes that row too. The Delete itself ends the row selection, so during a press that started on a handle or in its menu the subclass closes a stale menu only once the press and its click are over. Closing it at once hid the button under the pointer before the release, so the click landed on the cell below and no row was selected.

Crepe's view also kept every drag event in a table from ProseMirror, and cancelled dragover there but not dragenter. When the element under the pointer changes, Chromium sends only a dragenter, which happens on every update while the page scrolls under a still pointer. With that last update not cancelled, Chromium dropped a block dragged by its handle into the cell itself, as a copy of its text, and the block stayed where it was. With the last update a cancelled dragover, no one took the drop, so text from another app dropped on a cell did nothing. The subclass leaves the events of a drag that ProseMirror tracks in `view.dragging`, such as a block dragged by Crepe's block handle or selected text, and of a drag that carries text from elsewhere, such as another app or the Split view's Markdown pane, to ProseMirror, which cancels the dragenter and takes the drop. Crepe's block handle starts its drag on the handle itself, outside the editor, and only records it in `view.dragging`. The table keeps the drags of its own row and column handles, which carry no text, and drags of files, which the app takes, as before.

Crepe's drop indicator offers every block edge as a place to drop, including the edges between a table's rows and cells. A block put in there cut the table in two, or pulled a cell out into a new table. A drop whose nearest edge is inside a table therefore goes in above or below the whole table, at its edge nearer the pointer (`dropEdge.ts`). The indicator also had its own timing. It found its edge again only for a dragover at a new point, and otherwise kept the edge it found for that point. It hid its line 30 ms after a dragleave unless a dragover followed, and when the element under a still pointer changes, as it does while the page scrolls under it, Chromium sends a dragenter and a dragleave but no dragover. After such a scroll the indicator put the drop in at the edge that had been under the pointer before, which could be one between a table's rows, while its line stayed at its old place on the screen or hid. md-easy therefore removes the indicator's plugin and keeps only its state and the element that draws its line. A `handleDrop` prop of the editor view puts every drop in at the edge it finds from the page as it is at the drop, and a plugin of md-easy's draws the line at the edge the same code finds, on every dragenter and dragover over the document and on every scroll during the drag. The line hides once the drag leaves the document, which a dragleave whose related target is outside the editor, or missing as when the drag leaves the window, tells. It also hides at any drop or end of a drag in the window, in the capture phase on the document, so a file drop that the app takes before the editor hears it, or a drag cancelled with Escape, leaves no line and no work behind. Measuring every block takes long in a long document, since each `nodeDOM` lookup walks the blocks before it, so the code keeps the boxes of the blocks relative to the editor's box until the document or the editor's size changes, as the indicator kept its edges. A scroll moves the editor and its blocks together, so a drag that scrolls the page measures the page once. The line hides where a move would leave the dragged block or selection where it is, as the indicator did at its own edges. Crepe's block handle marks every drag it starts as a move, but ProseMirror decides at each drop, and copies while Ctrl, or Option on macOS, is held. The plugin therefore decides by ProseMirror's rule for the current event, so the line still shows for a copy right beside the dragged block, where the copy goes in. The page scrolls to show the drop when it lands out of view, as it can at the far edge of a tall table. A file dropped on a table goes in at the same edge (`fileDrop.ts`).

Crepe draws a fenced code block, math block or Mermaid diagram with a CodeMirror editor of its own, and its view keeps every event on the block from ProseMirror. CodeMirror took the drop of a block dragged by its handle, or of text selected in the document, onto the code. It put the text in at the pointer and, since it deletes only text dragged from within itself, left the original where it was, so the content was there twice. Over the block's toolbar or preview nothing cancelled the drag events, so nothing took the drop. For a drag that ProseMirror tracks in `view.dragging`, a listener on the editor in the capture phase now cancels each drag event on a code block before CodeMirror hears it (`dropEdge.ts`). CodeMirror ignores a cancelled event, and the cancelled dragenter and dragover allow the drop there. ProseMirror ignores the event too, since the block's view keeps it, so the listener puts the drop in itself with the code of the `handleDrop` prop, above or below the code block at its edge nearer the pointer, where the drop line shows, as for a table. Selected text goes in as a paragraph of its own there, as it does beside a table, rather than into the code. That keeps one rule for everything ProseMirror drags, and keeps a drop from mixing document text into code. Text dragged in from elsewhere, or within the code, is not in `view.dragging`, so CodeMirror still takes it at the pointer and shows its own drop cursor, and the drop line hides over the block. A file dropped on a code block goes in at the same edge as a block would.

Crepe fades a table's handles with opacity once the pointer leaves the table or nears a cell border, and leaves them, with any menu open in them, where they were. A faded handle, and a menu open in it, shows again as soon as the pointer is over it, so the user sees it before a click there. A column menu sits over the paragraph above the table. Before the subclass closed a menu after a content change, a click there right after a Markdown edit of a cell in the split showed a menu whose selection was gone, and the click selected the column, so typing then replaced the column's text.

Each tab owns its own document state, including its path, content, save status, and line-ending style. The save status compares the content with the text last read from or written to the file, or with the starting text of a document that has no file. A recovered snapshot counts as unsaved until it is saved, because the file may have changed since. While a save is being written, any edit counts as unsaved, because the file may hold either text. When the save finishes, the document stays unsaved if its text or line-ending style changed while it was written, and a change on disk recorded in the meantime with a later time stays the file's text. A tab also counts as unsaved while files dropped on its document are on their way into it. The tab records that apart from the save status, so a save that finishes meanwhile does not clear it, and opening a file never reuses that tab. A dropped file only goes into a document that is in front, so a drop that also holds Markdown files puts its other files in before it opens the Markdown files. A new tab would otherwise put the document behind it, and the files would wait until the user showed that document again. If the user shows another tab before the files are in, they wait for their document anyway, so the Markdown files open at that point. Otherwise the Markdown files would wait with them and take the front when the user came back to the document. The active tab is bound to the visible editor views.

Milkdown and CodeMirror manage their own editor DOM and lifecycles. React owns the surrounding application interface, including tabs, toolbars, dialogs, settings, recent files, and print views.

The document view marks an image that fails to load on the image's element, and CSS draws the missing-image placeholder or chip from that mark, so it never reaches the document or its Markdown. Crepe reports load errors only for images on their own line, so md-easy catches the errors of inline images itself. After each change to the document a missing image shows its node's current path, and it shows as an image again once one loads there. Crepe's image views look a file up only when ProseMirror passes them their node again, so after the user locates the path an image already has, a node decoration that lasts one transaction makes ProseMirror do that without a change to the document. Chromium paints no text selection over a chip, so a ProseMirror decoration marks the inline images a selection covers and CSS tints those chips.

Crepe's image views render a node's raw src until md-easy's lookup of its URL answers, and Chromium would request a relative src next to md-easy's own page. That request fails, logs an error, and can show the image as missing for a moment. So the document view looks a document's local images up before its first render, and a pasted or dropped image stored as a file waits for the lookup of its file before it goes in (`lookUpImages`). Each wait lasts at most a second, so a slow file system cannot hold a document or an image back for long.

Chromium's End does not move the caret from before an image or a formula that starts a line. On End the document view first moves the caret past the inline atoms there, such as images and formulas, and Chromium's End goes on from the text after them. Chromium cannot keep the anchor of a selection right after a line break and before such an atom. Each time Shift and a key that moves the caret, such as End or an arrow key, extend the selection there, Chromium moves the anchor before the line break. The document view puts the anchor back when ProseMirror reads the extended selection, and has ProseMirror read it before the next frame, so the line break never shows as selected. It types over a selection that starts or ends there itself instead of leaving the typing to Chromium. It takes the text from the beforeinput event, which carries all of it, such as both halves of an emoji, and which also comes for text put in without a key press. An input method's composition cannot be cancelled, so when one starts over such a selection, the document view first removes the selection and the composition goes on from the caret that leaves. It does that in the capture phase, before Milkdown's own handling of a composition at a caret between two inline nodes, which works only when the caret is there as the composition starts.

Milkdown's link mark is inclusive, so ProseMirror gave text put in at a link's end, and at the start of a block that begins with a link, the link. md-easy keeps that schema, because typing over selected link text needs it to keep the link, and Crepe's virtual cursor handles marks that are not inclusive poorly. Instead, after every change, a plugin gives a caret at a link's edge the marks there without the link as its stored marks. ProseMirror reads stored marks first for typed text, an input method's composition, a paste and commands such as Ctrl+B, and the virtual cursor draws its tail from them. Crepe's list item views put the selection back a frame after they are drawn, which clears stored marks, and the plugin sets them again in the same update, so a link dropped as a list item needs no rule of its own. Deleting a link's whole text, with Backspace, Delete or Ctrl+X, stores the deleted text's marks for the caret, which then sits inside the text around the link, so the plugin also takes a stored link off a caret that neither side of it carries. The plugin also tracks a link side, where typing goes into the link. The virtual cursor's Left at a link's end where text follows, and its Right at the start of a link that follows other text, set the link as stored marks without moving the caret, and typing over selected link text keeps the link. Each puts the caret on the link's side. Typing there keeps it there while the caret stays in the same text block, and so does Backspace or Delete that takes some of the link's own text, because ProseMirror gives the caret's next text the deleted text's marks. A move of the caret ends it. So does deleting the text on the other side of the caret, or the link's whole text, which leaves no link beside the caret in the marks its next text gets, and the virtual cursor then draws the tail on the plain side. Stored marks stay in the state while the caret rests at a link's edge, so find and replace clears them before it replaces a match, and text the browser changes away from the caret, such as a spelling fix, gets the marks of its own place. ProseMirror gives plain text that is dropped the marks of the place under the pointer, and the drop then puts the text in a block of its own at a block edge, so text dropped on a link became a new link to the same target. The plugin takes links off plain text that is dropped or pasted. A paste at the caret gets the marks there again, because Milkdown's paste reads stored marks. A file dropped right before a link to the same target, such as a missing attachment that the file fills, joins that link, so the caret after the file is inside one link. The drop makes that caret a plain caret, which the plugin tracks as it does the link side. The plain caret follows the caret while the caret stays where the edits map it, as typing, Backspace, Delete, undo and Milkdown's change of a heading's id after each edit of the heading do. Inside a link, it gets the marks there without the link as its stored marks, as a caret at a link's edge does. Stored marks alone did not last, because ProseMirror drops them on every change, and after Backspace or Delete gives the caret's next text the deleted text's marks. A link side ends a plain caret, and a drop ends a link side. The URL shown after a link is drawn before a caret at the link's end, where the next character goes, unless that character joins the link, as on the link's side. It is drawn after a selection's end at the link's end. Drawing the URL before a selection's end made Chromium type over the selection outside the link's element, which ProseMirror read as taking the link off the retyped text.

The URL after a link is CSS generated content of a widget element that holds only an empty comment, with no text in the DOM. For a plain click or Shift+click, ProseMirror leaves the caret where Chromium puts it and reads it back. Chromium has no caret position inside text that can be neither edited nor selected, such as a widget's text. For a click on such text it falls back to the start of the element under the pointer, which was the paragraph, because the URL takes no pointer events. Chromium puts a click on generated content after the widget instead, which ProseMirror reads as the link's end. The comment keeps an input method working right after the URL. Chromium treats a non-editable element with no children as one solid object, and with such an element a composition of more than one step went in twice, because Chromium dropped the composition and then put its committed text in as plain typing. With text in the element, even a zero-width space, Chromium lost the caret when a composition there was emptied, and the next one went in at the start of the paragraph. Because the URL is not text, word movement and deletion, such as Ctrl+Backspace, Ctrl+Left or a double-click, treat a link and letters typed right after it as one word, as they do when only the link text is shown. Print breaks a paragraph or heading only between the lines of its text, so the print copy writes the URL into the element as text and drops the attribute the generated content comes from. A heading whose URL wraps past a page then continues on the next sheet instead of being shrunk onto one.

md-easy opens a link on Ctrl or Cmd+click. ProseMirror selects the innermost block under the pointer as a node on a click with Ctrl, or Cmd on macOS, and the block around that on the next such click, so a Ctrl+click beside a link selected the whole paragraph or list item and the next key replaced it. The link plugin therefore takes every Ctrl or Cmd+click that reaches it and gives it the selection a plain click gets. Taking the click makes ProseMirror cancel the browser's handling of the release. Chromium keeps a selection that a press lands inside, because the press could start a drag, and puts the caret at the click only on the release. The plugin therefore puts the caret at a click inside the selection itself, such as in selected text, a block the block handle selected or the whole document. A selection with a hidden caret, such as a node or cell selection, gives way to a caret at a click next to it, as ProseMirror does for a plain click, because Chromium can report no change for a click at that hidden caret. Elsewhere the caret stays where Chromium put it on the press. A click that opens no link also selects a leaf node under the pointer, such as an image, and one that opens a link leaves the image unselected, so the next key cannot replace it. The URL after a link takes no pointer events, so a click on it targets the block around it, and the plugin finds the URL under the pointer by its box. The URL's widget sits right after the last character of its link, so that character names the link to open, never a link that follows. ProseMirror finds the link's end under the pointer on the URL, so a caret the plugin puts at such a click goes there, as a plain click's does. Crepe's link preview found its link from the position under the pointer, which on the right half of a character or on the URL is the position after it, where a link that follows starts. md-easy's patch of `@milkdown/components` has the preview take its link from the element under the pointer instead, as the click does. The preview's Edit and Remove act on a range, which Crepe took from the one node it found. A link of several nodes, such as an image with a caption after it or text around bold text, was then split, and Remove left the link on the rest. The patch gives them the run of nodes around that node that carry the same link mark, which Milkdown writes as one link.

Each code block is a CodeMirror editor, which handles its own clicks and adds a cursor on Ctrl or Cmd+click. A block that does not have focus keeps the cursor it had, at its start unless it had focus before, so a Ctrl or Cmd+click from outside the block added a second cursor there, and typing went in at both. md-easy gives Crepe's code blocks a `clickAddsSelectionRange` extension that adds a cursor only in a block that already has focus.

Chromium does not extend the selection on a Shift+click whose press lands on a link or an image, even in an editable element. On a link it puts the caret at the click, and a Shift+drag from there starts a new selection at the press. On an image it leaves the caret where it was. ProseMirror leaves Shift+click to the browser, so the link plugin handles a Shift+press on link text itself, and the image code one on an inline image. Each selects from the selection's anchor to the position under the pointer, or to the side of the image clicked. The link plugin then follows the pointer until the button is released. The anchor stays where the press found it, also when another plugin changes the selection in between. prosemirror-tables turns a selection that ends at the start of a cell into one of the paragraph it starts in, and an anchor taken from that selection stayed at the paragraph's start for the rest of the drag. A change to the document moves positions, though. Such a change can be a key pressed while the button is down, such as Backspace, or one made along with the selection, such as a typed closing `~~` that becomes strikethrough once the press takes the caret away from it. The drag then goes on from the anchor of the selection, which ProseMirror moved along with the change. After Backspace it goes on from where the key left the caret, as Chromium's own Shift+drag on other text does. While the pointer is above or below the document's scroll container, the plugin scrolls the container each frame by as far as the pointer is outside it, as Chromium's drag selection does, and extends the selection to the container's edge. prosemirror-tables handles the press first and selects cells on a Shift+click into another cell, and the plugin stops following a drag once the selection is no longer a text selection, as when prosemirror-tables selects the cells the pointer crosses. A press on an image inside a link is left to the image code. While the document view does not have focus, such as when a code block, the Markdown pane or the find card has it, the selection to extend is not the one the user sees, so a Shift+click puts the caret at the click instead. The link plugin leaves such a press to the browser, which puts the caret on link text. Chromium puts no caret on an image, so focus stayed where it was and the next key went in there. The image code therefore puts the caret at the side of the image clicked itself and then focuses the view. Focusing the view first would move focus back into a code block that holds the selection. The plugin extends the selection by characters. After a double-click selects a word, Chromium extends the selection by whole words. A page cannot read that state, so a Shift+click on link text then ends at the click. Because the plugin takes the press from ProseMirror, a Shift+double-click on a link to a Markdown file extends the selection instead of opening the file.

## Interface design

The interface follows the look of [Mervin PDF](https://github.com/lincarl/mervin-pdf). Dark mode uses Mervin's "Nord" chrome and light mode its "Cool slate" chrome.

- `src/styles/app.css` defines the chrome tokens (surfaces from the input well to the floating popover, inks, translucent edges and washes, the accent) for both themes and exposes them to Tailwind as colors such as `bg-well`, `text-ink-soft` and `border-line-push`.
- The primitives in `src/components/ui` (buttons, fields, check boxes, dialogs, menus, tooltips) carry Mervin's control styles, so surfaces compose them instead of restyling controls.
- Chrome icons are Lucide icons drawn at a 1px line weight.
- The document page keeps Crepe's 120px side padding while the text column can stay at least 400px wide. In a narrower editor, such as the Split view's document pane in an 800px window or the Document view in a 600px window, the padding gives way, down to 58px on each side. With the 24px the page or the pane adds around the editor, that still holds the block handle, which is 66px wide and sits 16px left of the text. CSS works the padding out from the editor's own width, so it follows the window, the split divider and the page width setting. With the default page width the Document view looks as before in windows 1000px and wider. A fixed page width below 688px narrows the padding in every window, so a 600px page has a 400px text column where it had 312px.
- The window's rows, from the toolbar to the status bar, share one grid column that is exactly as wide as the window, so no row can make the others wider. A row with more content than fits shrinks or cuts its own content. The status bar ends a path too long for it in an ellipsis, and its tooltip has the whole path.
- The document surface has its own light and dark palette, independent of the chrome theme. Find highlights use the same classes in the Document and Markdown views. The frontmatter table is outside the document editor, so its matches are CSS custom highlights with the same names and colors.
- The find card floats over the bottom right of the editor area and grows upward when its replace row opens. In a window too narrow for the card's top row, below about 610px, the card spans the editor area, less 12px on the left and 24px on the right, and Match case and Whole word move to a line of their own under the find field. The fields keep their width, and Close stays at the top right, so every control stays inside the editor area down to the narrowest window, 480px. Each find step scrolls the current match into view clear of the card, at whatever height the card has, centring it in the part of the page above the card when it was hidden or covered. When the end of a document stops the page short of that, the page gets room below its last line, as tall as the card reaches up into the page plus 12px, until the card closes. Find measures a match that wraps onto more lines by the box around all of its lines, not by its two ends alone.

## Application structure

The frontend is organized around a small observable application store and service modules for the major responsibilities:

- Document and tab state.
- File operations and external-change handling.
- WYSIWYG and source-editor integration.
- Paste, image, attachment, and link handling.
- Recent files, search, settings, and recovery.
- Printing and platform integration.

The Electron main process provides operations that require native access. File reads and writes, attachment storage, recovery snapshots, recent-file data, and settings persistence stay outside the renderer. A bundled preload exposes typed operations through Electron's context bridge. The renderer uses context isolation and sandboxing without Node.js access.

Packaged builds always load the bundled frontend and ignore development URL overrides. Unpackaged development launches accept only HTTP or HTTPS URLs on localhost, 127.0.0.1, or ::1, without credentials. Native commands accept only the authorized main frame.

The built frontend carries a Content Security Policy, defined in `vite.config.ts`. It blocks inline scripts, eval and scripts from the web, and allows images from the web, data and blob URLs, and local files. The development server goes without it. A feature that needs a new kind of resource, such as a frame or a web font, must add it to the policy.

## Data and persistence

User documents remain standard Markdown files. md-easy does not use a proprietary document format.

Application preferences are stored in `settings.toml`. Recent-file history and recovery snapshots are stored separately in the application's local data directory. File writes are performed atomically where practical to reduce the chance of corruption.

Settings saves use TOML syntax-tree ranges to update complete root values and insert missing settings before the first table. Quoted keys, surrounding comments, unknown data, a leading BOM, and existing line endings are preserved. Settings reads reject invalid UTF-8 rather than replacing bytes, and loading failures use defaults without changing the file. Before writing, the app checks that the result parses and contains exactly the requested settings plus the original unknown values. Invalid UTF-8, invalid TOML, or known settings expressed as dotted keys or table declarations remain untouched, and the app reports that saving failed. Known settings must use root key-value assignments.

Images can either live inside Markdown as data URIs or as files in a configurable attachments directory. Relative paths are used for attachment links so a document and its attachments can be moved together. A pasted or dropped file is written beside the document as it is saved when the file is written, because the user can save the document in another folder while a large file is read or written. FileService gives a document its new path only once a Save As has written it, so the paste or drop first waits for any Save As of its document that is under way (`FileService.untilPathSettled`). Before that it waits for the pastes and drops into the document before it to end (`EditorHost.untilTurn`), because its file goes in only after theirs. So a file is not stored and then held back while the user saves the document in another folder. If the document still moves to another folder while the file is written, the file is written again beside it. Its link then leads from the document's own folder, which always resolves and moves with the document, unlike a link back to the old folder, which cannot reach another drive. Pasted, dropped and uploaded images stored as files, an image chosen with Replace image, and other dropped files all go through this loop (`storeBesideDocument` in `src/images/imageStore.ts`). The lookup of a new image's URL (`lookUpImages`) runs inside the loop, before the check for a move, so a Save As that ends during the lookup writes the image again and looks it up again. An embedded image does not depend on the document's folder, so it skips the loop and never waits for a Save As.

A pasted image goes in through the same code as a dropped file (`FileDropCoordinator.pasteImages`), at the block edge at the caret, which is fixed when the image is pasted and which the document pane keeps in step with edits (`WysiwygEditor.caretTarget`). In a table, that edge is above or below the table, where the image goes in (`blockEdge`). An image pasted later at the same edge maps past the ones that went in there. Where an image takes an empty line, such as Crepe's last line below a final table or code block, it goes in before the line, which is then taken out, so a later target at that edge still maps past it. The files of a drop or paste also go in only once every drop or paste aimed at the same document before it has ended (`EditorHost.untilTurn`). Otherwise a later image that was stored first would go in first, and the earlier image, whose target maps past it, after it. So a file waits for a slow file dropped or pasted into its document before it, as the files of one drop do, and a drop's Markdown files, which open once its other files are in, wait with them. A file that goes in at a caret has no target that maps past earlier files, because the caret can stay before them. The files of one drop follow each other from the place after the one before. When a drop ends, it hands the place after the files it put in at a caret to the next drop of the document that is under way (`AimedDrop.follows`), whose files go in there while their own place is gone. That chain ends once no drop of the document is under way. EditorHost holds the image while its document is behind another tab, and counts the tab as unsaved until it is in (`Tab.filesPending`), as for a drop. Milkdown's clipboard plugin takes a paste that holds HTML or plain text, also when it holds an image too. An image alone on the clipboard, such as a screenshot, would reach Crepe's upload plugin, which stores it through the image block's upload hook and then puts it into the editor that took the paste. By then that editor can be rebuilt for an edit in the Markdown view, or dropped from memory behind another tab, which loses the image although its file was written. The upload plugin also puts in an image without a src when the save that an untitled document needs is cancelled, because the hook cannot cancel it. So md-easy's paste plugin takes such a paste in a DOM event handler, which ProseMirror runs before any plugin's `handlePaste`, and hands its images to the app (`WysiwygContext.pasteImages`). An editor built without that hook, such as the one print renders with, puts a pasted image nowhere.

A pane that a layout switch hid still takes a dropped or pasted file at its place while it holds the document's latest edit (`EditorHost.usable`). The document pane behind the Markdown view inserts the file and gives the Markdown view the matching change to its source (`insertMarkdownWithSource`), as the split does while the user types in its Markdown pane. The Markdown view's report of that change makes the tab's text newer than the hidden pane's, so md-easy then mirrors the text into the hidden pane, as the split mirrors it into a pane on screen (`EditorHost.mirrorInto`). The pane holds that text already and stays as it is, but counts as up to date again, so the drop's next file, or an image pasted after it, still goes in at its place. A mirror leaves a document pane's blocks alone while the pane's document is still the one the text gave it (`WysiwygEditor.setMarkdown`). The parse of the text can hold a block another way than the pane does, such as a list item with an image, which the text reads as loose and the pane holds as tight. Replacing that item would move the places of later files in it to its end. A change that any hidden pane of the document shown reports goes into the pane shown at once (`EditorHost` `onChange`). Without that, the pane shown would lag the tab's text, and `onChange` would drop its later edits as stale, so typing that stays on screen would be left out of the save. That also covers the image block's upload input and Replace image, which put the stored image into the editor that asked for it, even when a switch to the Markdown view hid it meanwhile. That editor reports the image after its usual pause, about 200 ms, so an edit in the Markdown view during the pause leaves the image out, and the edit stays. Once the hidden pane is behind an edit, or after a reload or a rebuild of the view, a file goes in at the caret of the view being edited. In the Markdown view, a file aimed at the document view then goes in as a paragraph of its own after the top-level block that holds the caret (`RawEditor.blockTargetAtCaret`), so it never joins the line the user types in, a heading, or the frontmatter, and never goes between the lines of a formula. Where that block is the last one and takes in text after it, such as a code fence or a formula that is not closed yet, the file goes in before it. A file that goes into the Markdown view is an undo step of its own there (`isolateHistory`), because CodeMirror joins a change without a user event to typing next to it within half a second.

The image block's upload input and Replace image put an image into the editor that asked for it, so they do not wait for a Save As (they leave out `ImageStoreContext.untilPathSettled`). A long wait would make it likelier that the editor is rebuilt or dropped from memory before the image goes in, which loses the image. They still write the image again if a Save As that ended while the image was written put the document in another folder. A Save As still being written when such an image is written leaves the image beside the old folder, with a link that does not resolve from the new one.

Attachment writes stage complete bytes in a sibling temporary file before publication. On filesystems with hard links, publication atomically claims a free name. FAT and exFAT use serialized application writes, a fresh name check, and atomic rename instead. That fallback preserves support for these filesystems, but another process creating the same name between the check and rename can have its file replaced.

## Desktop integration

Electron provides native windows, file associations, single-instance behavior, native open/save dialogs, opening links and folders, system appearance settings, and printing. Linux builds provide AppImage and DEB installers. Windows builds provide NSIS and MSI installers.

Undo and Redo in the native menus (the spell-check menu that Shift+right-click opens, and the macOS Edit menu) go to the renderer, which runs the focused editor's undo history. Chromium's own undo knows nothing of those histories. A plain text field, such as the find card's, keeps Chromium's undo.

The print workspace mounts a rendered copy of the document in the app window. Electron prints that document using the selected printer or writes a PDF. Printing waits for the workspace to finish rendering before starting the job. md-easy lays out the sheets itself and breaks pages between blocks. A block taller than a page continues on the next page. A paragraph or heading, and a line of the Markdown version, split between the lines they wrap onto, and inline formatting such as bold text or a link carries on across the break. A quote, a footnote, or a list item splits between the blocks it holds, and a table, list, or code block between its rows, items, or lines. What cannot be split, such as an image or a single table row taller than a page, is scaled down to fit the page instead of being cut off. A heading, or a run of headings such as a heading and its subheading, goes on the page of the first block after it that holds content, or of that block's first piece, so a page does not end with a heading whose text starts on the next page. Empty paragraphs, such as an empty line saved as `<br />` or one that holds only spaces, bold or not, and horizontal rules between them move with the heading. Elsewhere such blocks are packed like any other block. The Document version does this on the page and inside a split quote, footnote or list item. When the headings and that block do not fit an empty page together, for example before a piece of a split block that fills a page, the pages break as they would without the rule, since moving the headings would leave them alone on a page. The Markdown version prints source lines and keeps no line with the next.

The frontend can also run in a browser-backed development environment with platform operations represented by adapters. This allows most interface and editing behavior to be tested independently of the desktop shell.

## Design priorities

- Keep Markdown portable and directly editable.
- Make the formatted document view the default without hiding the source.
- Avoid content loss when switching views, tabs, or application sessions.
- Keep native capabilities behind focused backend services.
- Prefer a small, responsive desktop application over a broad workspace platform.
